# Заготовка для BPMN: развитие конструктора MiniApp

Документ описывает два состояния одного и того же продукта - платформы-конструктора цифровых продуктов и MiniApp:

- `AS-IS` - текущая версия конструктора, соответствующая ветке `TO-BE` из предоставленной BPMN-схемы: пользователь ищет готовое решение на платформе; если решение найдено, настраивает его по подписке; если не найдено, запускается более длинный путь через описание идеи, согласование, годовую подписку, разработку на унифицированной архитектуре, тестирование, релиз и поддержку.
- `TO-BE` - улучшенная версия той же платформы: логика продукта не меняется, но процесс становится быстрее и эффективнее за счёт prompt-driven создания MiniApp, автоматической генерации, проверок, preview и коротких edit-итераций.

Материал подготовлен как будущая вставка в исследовательскую работу и как основа для построения BPMN-диаграмм.

## 1. Концептуальная логика

В текущем `AS-IS` пользователь уже работает не с полностью ручной разработкой с нуля, а с платформой-конструктором. Сначала он ищет подходящий цифровой продукт на платформе. Если готовое решение есть, пользователь оплачивает подписку, заполняет необходимую информацию, после чего платформа автоматически интегрирует продукт. Если готового решения нет, процесс становится длиннее: пользователь описывает идею, идея прорабатывается и согласуется, оформляются шаблонные юридические документы, оплачивается годовая подписка, а продукт разрабатывается на основе унифицированной архитектуры. Затем выполняются тестирование, онбординг сотрудников, релиз и поддержка.

В целевом `TO-BE` сохраняется та же продуктовая идея конструктора, но тяжёлая ветка создания нового продукта сокращается. Пользователь описывает бизнес-процесс промптом, платформа принимает контекст, генерирует MiniApp, запускает автоматические проверки, показывает preview и позволяет быстро уточнять результат через edit-промпт. Таким образом, улучшение состоит не в смене платформы, а в ускорении и упрощении создания продукта внутри неё.

## 2. BPMN AS-IS: текущий конструктор

### 2.1. Дорожки AS-IS

| Дорожка | Назначение |
|---|---|
| Пользователь | Инициирует автоматизацию, ищет готовый продукт, оплачивает подписку, заполняет данные, описывает идею, участвует в согласовании и онбординге |
| Платформа | Предоставляет поиск по готовым решениям, принимает данные пользователя, выполняет автоматическую интеграцию готового цифрового продукта |
| Компания / команда платформы | Прорабатывает нестандартную идею, готовит КП и шаблонные юридические документы, разрабатывает продукт на унифицированной архитектуре, тестирует, релизит и поддерживает |
| Цифровой продукт | Готовый продукт, MiniApp или автоматизация бизнес-процесса, полученная пользователем |

### 2.2. Таблица процесса AS-IS

| № | Тип BPMN | Дорожка | От кого | К кому | Процесс | Результат / артефакт |
|---|---|---|---|---|---|---|
| A1 | Start event | Пользователь | Пользователь | Процесс | Возникает потребность автоматизировать бизнес-процесс | Процесс инициирован |
| A2 | Task | Пользователь | Пользователь | Платформа | Пользователь открывает платформу и ищет подходящее решение | Запрос к каталогу решений |
| A3 | Gateway | Платформа | Платформа | Пользователь | Найден подходящий цифровой продукт? | Решение: да / нет |
| A4 | Task | Пользователь | Пользователь | Платформа | Если решение найдено, пользователь оплачивает подписку на платформу | Активная подписка, 1890-7890 руб. |
| A5 | Task | Пользователь | Пользователь | Платформа | Пользователь заполняет необходимую информацию: данные бизнеса, сценарии, настройки, каналы | Заполненная конфигурация |
| A6 | Task | Платформа | Платформа | Цифровой продукт | Платформа автоматически интегрирует готовый цифровой продукт | Подключённое готовое решение |
| A7 | End event | Цифровой продукт | Процесс | Пользователь | Автоматизация бизнес-процесса получена | Быстрое завершение по готовому продукту |
| A8 | Task | Пользователь | Пользователь | Компания / команда платформы | Если готового продукта нет, пользователь составляет описание идеи | Описание идеи, 3-4 дня |
| A9 | Parallel gateway | Пользователь / компания | Процесс | Пользователь и компания | Проработка идеи запускается параллельно с двух сторон | Параллельная проработка |
| A10 | Task | Пользователь | Пользователь | Компания / команда платформы | Пользователь участвует в проработке и согласовании идеи | Уточнения пользователя, 1-2 недели |
| A11 | Task | Компания / команда платформы | Компания | Пользователь | Команда платформы прорабатывает и согласует идею | Согласованная концепция, 1-2 недели |
| A12 | Task | Компания / команда платформы | Компания | Пользователь | Формируются КП и шаблонные юридические документы | КП и документы, 1-2 дня |
| A13 | Task | Пользователь | Пользователь | Платформа | Пользователь оплачивает годовую подписку на платформу | Оплата 94 680 руб. |
| A14 | Task | Компания / команда платформы | Компания | Цифровой продукт | Продукт разрабатывается на основе унифицированной архитектуры | Рабочая версия, 1-2 месяца |
| A15 | Task | Компания / команда платформы | Компания | Цифровой продукт | Выполняется тестирование продукта | Проверенный продукт, 2-3 недели |
| A16 | Parallel gateway | Компания / пользователь | Процесс | Пользователь и компания | Запускается параллельный онбординг | Подготовка к запуску |
| A17 | Task | Пользователь | Пользователь | Сотрудники | Пользователь проводит онбординг сотрудников со своей стороны | Сотрудники готовы, 1-2 дня |
| A18 | Task | Компания / команда платформы | Компания | Сотрудники пользователя | Команда платформы проводит онбординг сотрудников бизнесмена | Проведено обучение, 1-2 дня |
| A19 | Task | Компания / команда платформы | Компания | Пользователь | Выполняется релиз продукта | Продукт выпущен |
| A20 | Task | Компания / команда платформы | Компания | Пользователь | Оказывается поддержка; исходный код остаётся у компании | Сопровождение продукта |
| A21 | End event | Цифровой продукт | Процесс | Пользователь | Автоматизация бизнес-процесса получена | Процесс завершён |

### 2.3. Шлюзы AS-IS

| Шлюз | Условие | Ветка `да` | Ветка `нет` |
|---|---|---|---|
| A3 | Найден подходящий цифровой продукт? | Подписка, заполнение информации, автоматическая интеграция | Описание идеи и более длинный путь создания продукта |
| A9 | Проработка идеи идёт одновременно? | Пользователь и команда платформы параллельно уточняют идею | Не используется, шлюз параллельный |
| A16 | Онбординг проводится параллельно? | Пользователь и команда платформы готовят сотрудников к использованию | Не используется, шлюз параллельный |

### 2.4. Краткая формула AS-IS

```text
Потребность -> поиск решения на платформе -> найдено? -> подписка -> данные -> автоматическая интеграция
или
Потребность -> поиск решения -> не найдено -> описание идеи -> согласование -> КП -> годовая подписка -> разработка на унифицированной архитектуре -> тестирование -> онбординг -> релиз -> поддержка
```

## 3. BPMN TO-BE: ускоренный конструктор

### 3.1. Дорожки TO-BE

| Дорожка | Назначение |
|---|---|
| Пользователь | Описывает бизнес-процесс промптом, проверяет preview, уточняет результат и подтверждает итоговый MiniApp |
| Платформа / Workbench | Принимает запрос, собирает контекст, управляет генерацией, проверками, preview и сохранением результата |
| AI-модуль генерации | Анализирует описание, генерирует MiniApp и исправляет найденные проблемы |
| Проверки / валидаторы | Проверяют сборку, маршруты, сценарии, сохранение данных и готовность preview |
| Preview / MiniApp | Показывает пользователю интерактивную версию и хранит финальный результат |

### 3.2. Таблица процесса TO-BE

| № | Тип BPMN | Дорожка | От кого | К кому | Процесс | Результат / артефакт |
|---|---|---|---|---|---|---|
| T1 | Start event | Пользователь | Пользователь | Процесс | Возникает потребность создать MiniApp для автоматизации бизнес-процесса | Процесс инициирован |
| T2 | Task | Пользователь | Пользователь | Платформа / Workbench | Пользователь открывает платформу | Открыт Workbench |
| T3 | Task | Пользователь | Пользователь | Платформа / Workbench | Пользователь вводит промпт: описывает бизнес-процесс, роли, задачи, данные и ожидаемый интерфейс | Описание продукта |
| T4 | Task | Платформа / Workbench | Платформа | AI-модуль генерации | Платформа принимает запрос и передаёт промпт вместе с контекстом | Запуск генерации |
| T5 | Task | AI-модуль генерации | AI-модуль | AI-модуль генерации | AI-модуль анализирует описание, выделяет роли, сценарии, сущности и ограничения | Внутренняя спецификация |
| T6 | Task | AI-модуль генерации | AI-модуль | Preview / MiniApp | Генерируется MiniApp: интерфейсы, backend-логика, маршруты, сохранение состояния | Черновая версия MiniApp |
| T7 | Task | Проверки / валидаторы | Платформа | Проверки / валидаторы | Платформа запускает автоматические проверки | Отчёт проверок |
| T8 | Gateway | Проверки / валидаторы | Проверки | AI-модуль генерации | Проверки пройдены успешно? | Решение: да / нет |
| T9 | Task | AI-модуль генерации | Проверки | AI-модуль | Если есть ошибки, AI-модуль исправляет результат | Исправленная версия |
| T10 | Task | Preview / MiniApp | Платформа | Пользователь | Если проверки пройдены, платформа открывает preview | Интерактивное preview |
| T11 | Task | Пользователь | Пользователь | Preview / MiniApp | Пользователь тестирует preview и проверяет сценарии | Пользовательская оценка |
| T12 | Gateway | Пользователь | Пользователь | Платформа / Workbench | Результат устраивает пользователя? | Решение: да / нет |
| T13 | Task | Пользователь | Пользователь | Платформа / Workbench | Если нужны изменения, пользователь уточняет промпт в edit | Edit-уточнение |
| T14 | Task | Платформа / Workbench | Платформа | AI-модуль генерации | Платформа передаёт уточнение вместе с текущей версией | Итерация доработки |
| T15 | Task | AI-модуль генерации | AI-модуль | Preview / MiniApp | AI-модуль дорабатывает MiniApp по уточнению | Обновлённая версия |

| Шлюз | Условие | Ветка `да` | Ветка `нет` |
|---|---|---|---|
| T8 | Проверки пройдены успешно? | Открыть preview | Исправить ошибки и повторить проверки |
| T12 | Результат устраивает пользователя? | Подтвердить и сохранить итоговый MiniApp | Вернуться в edit и уточнить промпт |

### 3.4. Краткая формула TO-BE

```text
Платформа -> промпт -> генерация -> проверки -> preview -> edit-итерации -> итоговый MiniApp
```

## 5. Сравнение AS-IS и TO-BE

| Критерий | AS-IS: текущий конструктор | TO-BE: ускоренный конструктор |
|---|---|---|
| Базовая логика продукта | Платформа уже является конструктором и содержит готовые решения | Логика конструктора сохраняется |
| Быстрый сценарий | Возможен, если готовый продукт найден в каталоге | Сохраняется, но дополняется генерацией новых продуктов |
| Создание нестандартного продукта | Через описание идеи, согласование, КП, годовую подписку, разработку и тестирование | Через промпт, генерацию, проверки, preview и edit-итерации |
| Участие пользователя | Поиск, оплата, заполнение данных, согласование и онбординг | Описание процесса, тестирование preview, уточнение результата |
| Участие команды | Существенное на нестандартной ветке | Снижается за счёт автоматической генерации и проверок |
| Время запуска | Быстро только для готовых решений; нестандартный путь занимает недели или месяцы | Быстрые итерации даже для нового продукта |
| Проверка результата | Тестирование выполняется отдельным этапом | Проверки встроены в цикл генерации |
| Доработки | Через согласование и ручную работу команды | Через edit-промпт и повторную генерацию |

## 6. Рекомендация по построению BPMN

Для `AS-IS` важно показать две ветки текущего конструктора:

```text
Найден готовый продукт -> подписка -> заполнение информации -> автоматическая интеграция
Не найден готовый продукт -> описание идеи -> согласование -> КП -> подписка -> разработка -> тестирование -> онбординг -> релиз -> поддержка
```

Для `TO-BE` важно показать, что продуктовая логика платформы не меняется, но длинная ветка создания нового продукта заменяется коротким циклом:

```text
Промпт -> генерация -> проверки -> preview -> уточнение -> итоговый MiniApp
```

## 7. Краткий вывод для исследовательской работы

В `AS-IS` платформа уже выполняет роль конструктора, но её эффективность зависит от наличия готового цифрового продукта. Если подходящее решение найдено, процесс короткий; если нет, пользователь попадает в длинную ветку согласования, оплаты, разработки, тестирования и релиза. В `TO-BE` сохраняется идея конструктора, но нестандартный продукт создаётся через prompt-driven генерацию, автоматические проверки и preview. Это сокращает путь от идеи до результата, снижает ручную нагрузку на команду и делает доработки более быстрыми и управляемыми.
